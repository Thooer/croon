# Croon

Croon 是一个运行 Agent 系统的内核。

它在 Agent 系统里的位置，有点像操作系统内核之于进程：Agent，连同普通的程序和人，以实例的形式运行在它上面；每个实例能做什么，由内核按它持有的权利检查；它做过的每一步，内核都记下来，崩溃之后照着记录恢复。这个类比只到这里为止。Croon 不调度 CPU，也不分配内存，它管的是权利、历史，以及谁可以纠正谁。

它与常见的 Agent 框架最根本的不同，在于把哪些东西放进了内核。创建一个 Agent、运行它、读它的历史、暂停它、给它换一件工具，这些在框架里通常是框架自己的代码，在 Croon 里是内核提供的操作，持有相应的权利才能调用。

由此有一件事值得先说。一个 Agent 如果被交给了构造与实例化这两项权利，它就能造出别的 Agent；而它自己，是经由同一个构造操作造出来的，运行的地方也正是这个内核。它调用的那件工具，和它脚下的这层框架，是同一个东西。从它的角度看，Croon 是一件可以调用的工具；从整个系统的角度看，Croon 是承载一切的框架，它也在其中。所以在 Croon 里，一个造 Agent 的 Agent，同时有工具与框架两重身份，两重身份之间没有要隔开的墙。

## 为什么做

我们做 Croon，是因为搭 Agent 系统时反复撞上同一类问题，而它们的根在同一个地方。

在常见的结构里，框架是最外层的程序，Agent 是它里面的一个循环。循环怎样转、子 Agent 怎样起、工具怎样接、出了错怎样收场，都写在框架的代码里。想换一种组织 Agent 的方式，要么改框架，要么在框架留下的钩子里绕路。Agent 自己更碰不到这些：即使它已经判断出某件事该交给另一个 Agent，它能做的也只是调用框架事先备好的那几种委托方式。

权限的情形相似。工具多半以函数的形式跑在框架的进程里，能碰到什么，取决于这个进程本身能碰到什么；子 Agent 通常继承父 Agent 的环境，一份密钥放进去，就跟着一路往下传。委托出去的权限，没有「收窄」也没有「收回」的说法。一个被某段文本说动的模型，最坏能做的事，就是整个进程能做的事。

于是治理只能从外面加上去：权限门、审批流、审计日志、策略引擎，一层层包在 Agent 外面。它们拦得住经过自己的调用，拦不住从别处绕过去的。长任务还有另一种脆弱：状态在内存里，进程一死，前面花掉的时间和模型调用一起作废；事后想弄清某一步是谁做的、凭什么能做，往往只能翻日志去猜。

我们的看法是，这些不是哪一个框架做得不够好，而是结构本身带来的：框架站在最上面，权利和历史是后来补上去的。哲学家 Searle 区分过两种规则。交通规则是调节性的：车先会跑，规则再去管它往哪里跑。象棋规则是构成性的：离开规则，根本没有「走一步棋」这回事。从外面加上去的治理属于前一种。Croon 想要后一种：在它的系统里，一个效果只能以「经某个 Port 交出」的形式存在，规则之外没有别的路。所以我们把次序倒过来，先有一个保证权利与历史的内核，再让框架作为普通的程序跑在它上面。

## 造 Agent 的 Agent

Croon 的内核只提供很少几样操作：把源码与接口构造成一份 Definition；把 Definition 实例化，运行成一个 Instance；以及对一个 Instance 的 Look、Notify 与 Correct，即读它的记录，在它结束时得到通知，暂停它、解除暂停或改它的接线。每一样都是一个 Port，持有指向它的 Reference 才能使用。

先看一个 Agent 拿到了构造与实例化会怎样。它写出一份新的程序，调用构造，得到一份 Definition；再调用实例化，让它运行起来，并拿到对方的 Port，向它交一件事；对方结束时，结果送回到它手里。这几步原本是框架的工作，现在是它的工具调用，和读一个文件、跑一条命令没有区别，都是持有某个 Reference 之后经某个 Port 交出一次，都记在它自己的 Journal 里。

再看这个 Agent 是怎么来的。它同样是被构造、被实例化出来的：系统外的根通过 root entry 调用内核的构造，造出这份 Definition，再把它实例化。根用的，与它之后用来造别人的，是同一个操作。这一点是关键，它让整件事首尾相接：造的一方与被造的一方，守同一套规则，记在同一种 Journal 里，受同一种权利检查。一个 Agent 造出的 Agent，不会因为是它造的而获得它没有的权利，也不会因为位置在它下面而被排除在规则之外。

这就是我们说它同时有两重身份的意思。对这个 Agent 而言，构造与实例化是它调用的工具，是它手里的东西；对整个系统而言，内核是承载所有 Instance 的框架，是它脚下的东西，包括这个 Agent，也包括它造出的每一个。手里的和脚下的是同一个，所以我们不需要为它另设一层元框架，也不需要一个在所有 Agent 之外的编排者：编排本身就是 Agent 能做的事，只要有人把相应的权利交给它。

这是机制所允许的，不是说每一层我们都演示过。造出来的 Agent 能不能继续往下造，只取决于有没有人把构造与实例化接给它，内核不替任何一方设上限；实际走到几层，由交办的一方在接线时决定。我们自己的应用只走了一层，原因与默认的做法写在 croon-app 里。

监督同样可以单独授予。Look、Notify 与 Correct 是三个分开的 Port，可以交给不同的一方：审计者只拿 Look，熔断者只拿收窄到只能暂停的那一份 Correct。Correct 由内核执行，被纠正的一方拒绝不了；内核还从结构上拒绝让任何执行者持有指向它自己、或指向它所属团队的 Correct。控制一个执行者的开关，装在它自己够不着的地方。

## 权利模型

Croon 的权利模型沿用对象能力（object capability）的思路：权利就是对某个对象的引用，持有它才能用它，此外没有别的授权方式。

系统里只有一种权利，叫 Reference。一个 Instance 得到 Reference 只有三条路：它实例化了别人，于是拿到对方提供的 Port 与对它的 Control；别人把手里的 Reference 接到它需要的 Port 上，在实例化时或运行中；或者别人交给它东西时，把 Reference 随附带过来。三条路上，内核检查的是同一件事：给出去的，不超过给的一方自己持有的。Instance 手里拿着的只是 Handle，每个 Instance 一份 c-list，Handle 只在自己的表里才有意义。知道别人的 Handle、写出一个 ID，什么也得不到。系统里没有全局的注册表，也没有谁都能取用的共享上下文。模型、提示词和生成的代码，都不是权利的来源。

权利在传递中只会变窄。每转交一次，接收的一方声明的限制就作为一节留在派生链上；每次使用，内核把整条链上的限制合在一起检查，安全不必依赖去判断两份规格之间谁包含谁。转交出去的权利可以收回：撤销沿着派生链往下传，立即生效，下游的每一份同时失效，不相干的持有者不受影响。

这带来两个实际的后果。其一，一个 Instance 被一段文本说动之后，最坏能做的，也只是它持有的那些，而不是它所在的进程能做的全部。其二，它能拿到的权利有一个上限，这个上限在运行之前就能从接线与声明里算出来，不必等出了事再去翻日志。

权利只能转递和收窄，能力却可以在组合中增长。几个 Agent 组成的团队，能做好的事可以超过其中任何一个；它能对世界造成的效果，却始终落在成员手里那些权利的范围之内。我们希望 Agent 越组合越能干，而它们能造成的损害不随之扩大，权利模型就是为这件事设计的。

## 记录与恢复

每个 Instance 的每一步都记在只追加的 Journal 里，任何时刻的状态都只是这些记录的投影。跨实例的事件，比如一个 Instance 的诞生、一次交出与它的到达、一次撤销，在同一个事务里落盘，记录之间不会互相矛盾。

进程被杀、机器断电、宿主出了故障，修好之后都从记录接着走：完成过的步骤不重做，发生过的事不改写。我们的测试在每一个提交点的前后注入崩溃，要求恢复之后得到的 Journal 与从未中断时相同。任务自己的失败如实记下；宿主的故障则让受影响的实例停下、保留现场，等宿主修好后重开，不会被错记成任务的失败。

对 Agent 系统来说，这意味着已经付了钱的模型调用不会因为一次崩溃而白付，长任务可以断了再续，而每一步都答得出：谁做的，用了什么，凭的是哪一份权利。

## 不只是给 Agent 用

内核里没有模型、提示词或推理这些概念。模型只是驱动 Instance 的一种方式；一段只做算术的程序、一个由人在系统外操作的入口，在内核看来与它是同一种东西：一个持有 Reference、每一步都记在 Journal 里的主体。同样的规则因此对程序和人也成立。我们的测试里有一个完全不用模型的审批场景：两类意见经入口交进来，一个固定的审批程序给出决议，中途重启也照样恢复。

把这一点往前推，Croon 想成为一台执行制度的机器。谁能做什么、谁做了什么、谁可以纠正谁，写进 Definition，就由内核兑现；几方如何分工、谁监督谁，写成 Charter，结构由内核守着，成员中途被说动了，结构也不会跟着改变。分权与监督靠结构成立，用不着指望每个参与者自觉。这是我们看得最远的一个目标，也是离完成最远的一个：今天 Charter 只做到了实例化，团队的终止与对整个团队的纠正都还在设计里。

在 Agent 这一侧，我们给自己定的目标是兼容：别的 Agent 框架有的功能，在 Croon 里都应当能用组合做出来。做不出来的那一处，就是内核还缺的东西。

## 三个仓库

| 仓库 | 是什么 |
|---|---|
| croon（本仓库） | 内核：Reference、Journal、构造与实例化、Control，以及它们对外公布的契约 |
| [croon-lang0](https://github.com/Thooer/croon-lang0) | `lang0@1`，Agent 写程序用的第一种 Language：写法是 Python 的子集，求值确定 |
| [croon-app](https://github.com/Thooer/croon-app) | 第一个应用：一个在容器里改代码、会在运行中自己造 Agent 的命令行工具 |

依赖是单向的：croon ← croon-lang0 ← croon-app。本仓库不认识上面任何一层。

## 现在

设计正在被实现检验。已经实现并有测试的：持久执行与逐提交点的崩溃恢复、显式的 Bundle 交付与读取资格、派生链的合取与撤销、Control、宿主故障的局部停机与重开；Charter 能实例化，Collective 与它的成员在同一个事件里诞生。

还没有的：构造时核对写死的 Definition 满足它的 Seat、Collective 的终止与对它的 Correct、多个 Entry 的系统边界。未决的问题写在各部分末尾的「待定」里。

## 接入

本仓库是独立的 Cargo workspace，`cargo test --offline` 跑完全部测试，不需要上层仓库。

公开的契约是三个 crate：`croon-eval`（Value、Schema、Bundle、Definition 与 Language 的求值契约）、`croon-port`（Port 与内容交付）、`croon-tree`（目录内容格式 Tree）。提供者与 Language 只依赖它们；`kernel` 是运行时，装配系统的宿主才依赖它。按角色读，不必通读文档：

| 你在写 | 先读 |
|---|---|
| 宿主 Port（模型、文件执行等） | `croon-port` 的 crate 头部 |
| 一种 Language | `croon-eval` 的 crate 头部 |
| 宿主：装起系统、驱动 root entry、处置宿主故障 | `kernel` 的 crate 头部；最小的宿主在 `crates/kernel/tests/host.rs` |

crate 头部只写必须做什么，理由指回 docs 的具体小节；读完头部还得去读实现才弄得清的行为，是文档的缺口。文档入口是 `docs/README.md`，系统设计从 `docs/Kernel/README.md` 进入。代码里用的 JSON 形状以各 crate `schema/` 下的 block 为准。
