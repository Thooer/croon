# DSH

DeepSeek Harness：一套把可逆性、依赖响应性与可观测性做进运行时的 Agent 底座，插件内核是 Cordis，见 先例.md 的「扩展的边界」。下面只留能用得上的线索：支持某条已有前提的、指向 Kernel 的缺口的、或让某个待定变小的。全部待核验：来自网页端的调研与讨论区，没有对照源码与论文，只作线索。

## 模型能看到的，必须能从记录里重建

研究观察：DSH 每次请求发出前先写日志，再构造请求，并用运行时断言守住「模型能看到的等于记录里的」。TUI 在恢复时只回放日志，不做额外拼装。

研究观察：这条约束有可见的代价。一个社区插件要给中途插话加一段「这是插话、不是新任务」的语义框，只能把它放进用户消息里；走隐藏通道就违反这条约束。

我们的推断：这与 Journal 的「上下文只放当前值」「交给 llm 的 Value 是一条交出记录」是同一条判断的两半——Croon 没有隐藏通道可走，所以不需要一条断言来守：进上下文的东西只能是一条交出记录。这条线索支持前提「早先的值压制后来的」那条做法的代价是显式的：要藏，就得改记录。

## 可逆副作用，与它没有的那种环境

研究观察：Cordis 的时间可组合性要求组件卸载时把它对共享环境做过的每一次修改完整逆转，落成「凡注册皆走 effect，每项自带清理路径」，于是系统行为只取决于最终启用的插件集合，与加载顺序无关。作者的说法是：Agent 能改自己的运行时之后，卸载才成为刚需。

研究观察：代价随耦合度增长，社区反复提到组件交互成本随插件数近似平方增长；作者把卸载标成 deliberate opt-in，默认路径不依赖它。

我们的推断：Croon 没有可以污染的环境，所以没有「逆转」这件事：权利是 c-list 里的一项，效果记在 Journal，撤销只让权利失效，不回滚已经发生的效果。这不是同一机制的另一种写法——Cordis 的问题在 Croon 里被结构消解了，不是解决了。留下的真问题是它在别处也解决不了的那半：试错不留下污染。Croon 的试跑留下 Journal 记录与花掉的 token，见 Library/Organization.md 的待定「试跑与固化」。这条线索让那个待定的形状变小：要问的是「试跑留下的东西算不算一份资产」，不是「怎样回滚」。

## 缺一个 provider 时静默挂起

研究观察：Cordis 的依赖注入在运行时解析，组件用 static inject 声明需求；缺任何一个底层 provider 不报致命错误，而是让下游组件静默进入 pending，一个漏配的底层节点可以级联让三十多个插件一起卡住。

我们的推断：这是 Required port 在实例化时静态检查、缺一个就以 type 失败的理由的直接证据：运行时的隐式拓扑换来的表达力，代价是失败的位置与原因都不可见。Croon 的接线在构造与实例化时查完，见 Kernel/Definition/README.md 的「Charter」的「检查」。

## 一个接缝上的多个使用方，可以各自和隔离发生不同的关系

研究观察：常规的文件与 Shell 路径都走内核级沙箱接缝，但 Code Mode 的 run_code 把模型写的 TypeScript 交给 worker thread，在空环境与预算下执行，没有文件效果约束，与宿主共享 UID，可以直接 import node:fs 与 node:child_process。在同时启用只读或工作区可写的部署里，它是对文件沙箱的完整逃逸。社区有把 Code Mode 放进容器、无网络、只读 rootfs 的替代实现，但要显式替换 provider，不是默认路径。

我们的推断：这条不指向 Lang0（Lang0 只产生 Atom，本来就不运行不受信代码，见 Kernel/Definition/Cognition.md 的「求值契约」），只指向 Plugin：可替换性本身不保证一致性，同一个接缝上的几个使用方可以和隔离各自发生不同的关系。Croon 对这一点已有要求：Plugin 的 Port 要声明属于通道的哪一行，有世界效果的还要声明上界与中断后的状态，写在 Kernel/Reference.md 的「通道」。这条线索只说明那条要求为什么在那里，不指向新机制。

## 可逆性不处理运行中的资源失控

研究观察：DSH 的 Agent 循环没有内置的 max-step、token、cost 熔断；讨论区有记录称一个看似简单的任务烧掉一亿多个 token，因为循环在模型持续产生工具调用时不会主动停止。可逆性处理的是卸载后的状态回滚，不处理运行中的资源失控，两件事由不同的机制负责，且部分尚未默认启用。

我们的推断：这是 Lang0 的 B、L、W 与 Library 的 max_turns 分成两处的旁证：一步之内会不会跑飞，由 Language 按 Surface 的运算计；跨轮的花费，由 Library 的预算者管。Kernel 两边都不管，见 Kernel/Reference.md 的「通道」。

## 在途的流式输出是一条事件

研究观察：它的内部不是「模型、工具、模型」的朴素循环，而是一条可被监听的流水线，llm/stream 与 tool/call 各是一个扩展点；不同的扩展点选不同的分发模式，其中门禁是 waterfall，返回类型化的决策联合，而不是裸的布尔值，使多个策略可以确定地组合，而不是在优先级冲突里静默覆盖。

我们的推断：两条。一是流式生成在它那里是流水线上的事件，所以「模型的输出到一半」有位置放；Croon 的在途 Atom 没有记录，见 Kernel/Reference.md 的待定「在途 Atom 的事实」，这条线索不改结论，只说明缺的是什么：一个在途的位置，不是一种新的记录。二是几个策略包装同一个交出时的组合必须确定——Croon 的 Middleware 靠嵌套的写法定顺序，写在正文里看得见，与类型化决策要解决的是同一个问题，不另设机制。

## 它不给 Kernel 添什么

我们的推断：逐项对照之后，需要 Kernel 新机制的没有一条。有的已被现有概念覆盖，差别在 Croon 更严（接线静态查完、没有隐藏通道、没有共享的 Context）；有的在 Library 层用现有机制组合，如多个策略包装、试跑的接线；有的明确拒绝，如把模型写的代码直接跑在宿主里，与运行在共享 Context 上的插件互相协作。它自称的「Agent 的下一层抽象是运行时可修改性」在 Croon 里是 Handoff 与 construct，不是卸载。
