# Reference

Reference 是唯一的权利：Instance 持有的、指向某个 Port 的东西。持有它，就能经这个 Port 交出；没有它，就做不了。模型、提示词、生成的代码都不是权利的来源。

一切效果都经 Port：框架不隐式交给谁任何东西、不隐式触发行为、不绕过 Port 改状态。所以任何一次行动都能回答谁做的、用什么、凭什么。

Reference 由 Kernel 持有，Instance 手里只有 Handle。Handle 由 Kernel 生成，格式见 Instance 的「ID」；全局不重复，用过不再用，记在 Journal 里；它就是这个 Reference 的 ID：持有者用它交出，别人用它指认。Handle 本身不带权利：知道别人的 Handle 或 Instance 的身份，不等于对它有任何权利，能不能用看自己的 c-list。这是对象能力模型（ocap）里 c-list 的做法，不是凭据即权利（bearer token）。不复用，是因为重放时记下的 Handle 必须永远指同一个 Reference；全局不重复，误放进 Value 的 Handle 就解析不到别人那里去。c-list 每个 Instance 一份，不全局共享：全局的服务注册表就是环境权利，所以不设共享的 Context。

## 提供者

每份 Reference 所指的 Port 都由 Journal 与 Value 唯一确定。派生继承所指的 Port，沿来源追溯；接收方的诞生、到达与授予记录解释它获得了哪一份。派生时增加的收窄见「限定」。

| 提供者 | 提供什么 |
|---|---|
| Kernel | pack、构造、实例化、对 Instance 的 Control、撤销权，形状见 Port |
| 别的 Instance | 它的 Provided port |
| 宿主 Port | 模型、隔离执行、检查服务及出站服务；只有 Port spec，实际实现由宿主按来源接入 |

账号是带身份的 Reference，指向外部服务为某个身份开的 Port。它在系统里没有来源，只能从根进来；之后和别的 Reference 一样往下收窄。联网分两种：匿名访问公开网络，范围宽，主要风险是外泄；以某个身份访问某个服务，范围窄，主要风险是这个身份被滥用。

## 获得

进来的 Reference 只有两个去处：放进一个 Required port，或者成为一个新的 Handle。交出时用 Required port 的名字与用 Handle 是同一种操作；运行中拿到的 Reference 能直接用。对应 ocap 的三条路：

1. **实例化**：实例化的一方得到 Agent 每个 Provided port 的 Reference，加上对它的 Look、Notify 与 Correct，各是一个新的 Handle，可以分开转交。实例化一份 Charter 得到的 Port 从占着那个 Seat 的成员的 Provided port 派生，链上有 Seat 与 Collective 的 Interface 写的两节：外面的一方只能按 Collective 的 Interface 交出。
2. **接上与授予**：实例化时，把自己持有的 Reference 接到 Agent 的 Required port 上，并检查每个 Required port 都接上了；运行中，持有 Correct 的一方经授予放进去。成员由 Charter 接上，来源见 Definition 的 Charter。
3. **附带**：交出时随 Value 带上自己持有的 Reference。Kernel 检查、记下派生，给接收方新的 Handle。Value 里写着的 Handle 不算数：Value 只给出信息。

三条路都满足"给出的不超过自己持有的"，都由 Kernel 检查。三条路上，接收方为这个名字写的声明（Required port 的 Port spec、附带声明里的那一项），都要与派生后链上另外某一节相同，或者写的是不限；否则交出的一方以 type 失败。这一条只为把错记在交出的一方：安全靠「限定」里的合取，不靠它。「相同」的定义与放宽见 Definition 的 Port。所以 Reference 在组合中只能转递、收窄，Competence 却可以增长：一个 Collective 能造成的效果，总在成员持有的 Reference 之内；它能做好的事，可以超出任何一个成员。

- Instance 不天生持有指向自己的 Reference：实例化它的一方或 Charter 把它的某个 Required port 接到它自己的某个 Provided port 或它自己的 Look 上，Kernel 在诞生时派生出这一份，所以它一开始就有。这一份从那个 Port 派生，派生链的最上方就是它；给不给，由实例化的一方或 Charter 定。
- 不持有指向自己的 Correct：Kernel 拒绝让一个 Instance 经附带、接上或授予持有指向它自己、或包含它的 Collective 的 Correct。Control 分成三个 Port，所以这是看 Reference 指向哪个 Port 的结构判据，不分析 Port spec。「执行者不持有指向自己的 Correct」由此强制。
- 没有来源的 Reference 在 root entry 诞生时接上，binding.sources 明确所指是 Kernel 操作或宿主提供者恢复身份，保存实际 Port spec；wire 中的 Handle 指认来源。第一节用来源规格的内容 ID 与空 Pointer，第二节用 root entry 自己的声明；相同比较忽略 description，链保留两份准确内容。派生继承所指，不用接收方名字或同形规格重新选目标。宿主装配具体模型、地址、凭据和通道实现，不新增持久服务注册表。
- 到达带来路：交到哪个 Port、谁交的、沿哪一份来。来路沿派生链往上，报第一份由接收方自己交出时派生的；没有，就报所经的那一份。所以经转交者回来的回复，接收方仍按自己交出的那一份认出，看不到中间各方的 Handle。要匿名，就经转交者转交，接收方看到的交出者是转交者。
- 转交不改变来处：持有别人的 Provided port，只是持有它，不成为它的 Principal。

## 撤销

每次附带、接上、授予，Kernel 都从给出的 Reference 派生出新的一份，交给接收方，记下派生链；链的每一节记着什么，见「限定」。交出的结果对每个附带给出两样：

- **派生出的 Reference 的 Handle**：就是接收方手里的那个，也出现在接收方那项到达的来路里。交出的一方凭它认出对方沿这一份交回来的东西。
- **撤销权**：一个 Reference，指向 Kernel 提供的 Port，作用在这一次派生上。它与 Control 同一类：Kernel 提供、作用在 Kernel 对象上，被作用的一方拒绝不了；可以转交，可以收窄。比如只把"撤销给 B 的那一份"交给监督者，不必交出源 Reference。

撤销沿派生链递归，否则撤销会有漏洞。一次撤销是一次事件：每个受影响、还没结束的持有者的 Journal 各记一条失效，在同一个事务里写下；之后再用被拒，被拒也记。持有者是 Kernel 的，如 Notify 登记里接下的 `to`，没有一本 Journal 持有它，撤销只留下撤销的一方那一步：它没有造成别人的记录，所以不违反「事件对得上」。

## 限定

一个 Reference 可以比它的来源更窄，比如只能向某个服务交出某种形式的东西，只能对一个 Instance 做暂停。限定就是声明：写在一个位置上的 Port spec 与附带声明，是对经过这里的 Reference 的收窄，不另设表示。

- 派生链的每一节固定经过位置的 Port spec，记成其内容 ID 加 JSON Pointer。完整规格从根 binding、诞生 Definition、结果附带及撤销权取得；self Look 使用共同 Look 规格。转交后 incoming.spec 交付第一节的完整内容，后续收窄仍留在链上。
- 经一份 Reference 交出时，Value 要满足链上每一节的 in，附带的名字要每一节的附带声明都允许、required 的都带上。
- 被附带的那份保留自己的链，再接上所经的那份 Reference 链上每一节对这个名字写的声明：交出的一方写的、接收方写的、中间收窄过的。写的是不限的，不接。
- 失败记在经这份 Reference 交出的一方。违反的节里有它自己为这份 Reference 写的，是 type；只违反别人加的节，是 denied。它没为这份 Reference 写声明的，提供者那一节算它自己写的。附带不合接收方写的声明，也是交出的一方 type，见「获得」。接收方在这次交出里不失败。
- 链是索引，能从 Journal 的派生记录加 Definition 重建，不另记。所以重建时会重新解释的三样，有了真实数据就改不了：派生时接上哪些 Port spec；节的记法，Port spec 的 ID 加位置；附带声明怎样解释，它写在已冻结的 Definition 里。改了任何一样，已经持有的 Reference 以后交出时的合取就变了，等于追溯改变权利。接收方的比相同、notify 接下时的检查不在其中：它们的结果记在 Journal 里，重建不重算，可以放宽；notify 的放宽仍要保守，不接下以后交不过去的 `to`。

只查提供者与现在的持有者两侧不够：登记者交回一份只能暂停的 Correct，持有者再把它附带给一个声明了完整 Correct 的一方，登记者那一节就丢了，授权变宽。所以每一节都留在 Reference 上，每次交出都合取。安全只靠校验器，不需要判断一份 Port spec 是否比另一份窄。

- 判断必须确定：相同的输入得到相同的结论，与比较的顺序无关。合取满足这一条。
- 只写通道强制得了的限定，写了强制不了的等于没写。
- 限定只查形式；内容与状态的规则由保管者承担，见「持有意味着什么」。
- 次数是一种容量，不是限定：派生链上的每一节都是无状态的。要限次数，就在派生时把下一次转交的那一份一并交出，用完就没有下一份；或由保管者按计数规则转交，到次数后结束。它结束后再交给它被 Kernel 拒绝。

## 持有意味着什么

- **持有别的 Cognizer 的 Port**，能借它的行为造成效果，上限是它自己持有的 Reference；持有者不需要那些底层的 Reference。
- **保管者**是持有 Reference 或状态、经 Port 按自己的 Definition 提供访问的 Instance。使用方没有绕过它的途径，所以受它的规则约束；判定只在它持有的范围内收窄，不产生权利，也不取消上游的撤销权与 Control。它是组合，不是新的 Instance 种类。
- **Interface 的形状由 Kernel 检查，功能由做法兑现。** 通过形状检查，只说明这次交互合声明；内容会怎样影响后续行动，取决于程序怎样处理它。一个 Cognizer 可能在已有权利内做出功能约定之外的事，所以敏感 Reference 要收窄到任务所需。只查形式的规则用限定，由通道强制；要看内容或几条连接上的状态，由保管者按选定的规则检查。规则归组织固定时，用 Charter 的 pin 与接线，规则实现的正确性见 Definition 的「Seat」。
- 私有数据、不可信输入、对外通道集中在同一个 Instance，输入处理中的一次错误就可能把私有数据交出去。需要阻断这条路径时，把数据与通道分给不同的成员，并检查它们能经 Port 交换什么；同一个 body 内的函数仍共用这个 Instance 的权利。运行中才拿到的 Reference，查得了的只是可达的上限：附带声明不是 true、叶子也没有 true 时算得出，见 Definition 的「附带的声明」。
- **知道就能用的东西不进任何数据**：密钥、密码、令牌、cookie 不进 Definition、输入、交出的 Value、Bundle、Journal。抄数据就抄走了权利，绕过收窄检查；读到过的拿不回，撤销做不到；进了上下文和只追加的 Journal 就永久留存；带出 Croon 使用时没有记录。凭据只在 Kernel。

Kernel 提供的 Port 与它们的形状见 Port.md。

## 能读的 ID

信息取得有两种关系：普通内容只读该 Value；Bundle 根可读描述、content 与依赖闭包。两者分别记在资格索引中，不能因普通内容满足 Bundle 形状而提升。对象已存在、对象合法与某个 Instance 已取得它分别成立。字段中普通 ID 不自动展开。

每条记录确定一份交付集合，Look 只合并所选记录的集合。记录没有提供的 ID 不从目标的当前范围补齐；读取 Look 的历史结果也只使用该条记录写下的集合，不递归猜测嵌套字段。

| 记录 | 普通内容 | Bundle 根 |
|---|---|---|
| 诞生 | input 的 Value；来源规格与自身声明的规格 | definition、input.dependencies；成员固定输入来自其 Definition 闭包 |
| 交出请求 | 请求 Value；已记录的附带规格 | accepted 为 true 时的请求 dependencies，含业务失败 |
| 交出结果 | 完整 outcome 的 Value、进来与派生 Reference 的规格 | outcome.dependencies，与业务成功与否无关 |
| 到达 | delivery.value 和附带规格 | delivery.dependencies |
| 取 | 已取到达的同一集合 | 已取到达的同一集合 |
| 结束 | 完整 outcome 的 Value | outcome.dependencies |
| Correct、失效 | 记录本身与明确给出的规格 | 无 |

记录自身是 Look 的输出信息。上述普通内容先落盘，其 ID 能由记录直接算出；Journal 不枚举一份可从载荷推出的副本列表。失败请求声称的依赖不在取得集合里；其 Value 仍是已经写出的普通信息。

每次交付先查给出者在接受位置的资格，再固定实际根。宿主提供者只读本次请求闭包，产物只能引用这个范围与本次新写内容；越界是宿主故障，保留执行身份并停下。合法产物与错误业务 out 分开：后者改为 use，前者仍明确交付；错误 Reference、候选诞生和到达不提交。

pack 把调用者提交的内容和本次交付的依赖建立为新根。读到一个 Bundle 描述文件只能再把它当字节封装；要建立它所描述的依赖，仍须逐项有资格给出。construct 只建立检查事实，instantiate 另查完整根、事实和授权；二者不再是读取模式。

### 求值中的读取位置

Kernel 的实际取得范围与 Language 的程序可见范围分开。后者初始只含诞生；之后每个分支只在消费一个 Atom 结果时取得该结果的交付集合。尚未消费的结果、提前写下但尚未取的到达不影响纯读取。恢复虽然可一次给出全部结果，Language 仍按相同程序顺序消费；并行分支各自保留消费过的键集合。

受控 Read 请求带本分支已消费的结果键。Kernel 只据诞生和这些真实存在的结果提供内容；指定取结果时沿它固定的到达展开，不能直接指定任意到达序号。检查 Definition 时 Read 固定为该 Definition 闭包，不接受业务结果键。求值器的消费轨迹由 Language 契约负责，Kernel 检查键真实存在和可读范围，不声称判断某个纯计算执行到了哪里。

求值器谎报已消费键属于违约；它仍拿不到本 Instance 未取得的信息。正确求值器的纯读取只依赖诞生和已消费结果，与重启、调度及结果送回顺序无关。Entry 没有可重放的程序位置，读取按它实际取得的范围执行。

读不到与不存在都以 denied 或读取失败表示，不以不同错误泄露对象存在性。构造事实只在根已取得之后查询。案例：先读 X 失败、一次取之后取得 X，再读成功；恢复也保持这个先后，不能用最新索引改变第一次读取。难改的点是普通内容与根的区分、记录的交付集合、分支消费轨迹。

## 通道

通道决定接受之后的物理效果怎样收齐，不解释产物的领域内容。

| 通道 | 暂停 | 进程崩溃后 |
|---|---|---|
| 无世界效果 | 丢弃，继续时重做；丢弃的模型调用仍可能收费 | 从固定请求重做 |
| 隔离执行 | 有上界地收尾，记录稳定结果；不继续 body | retire 旧 attempt，确认写者和迟到启动已封住，再按接受快照重做 |
| 系统内事务 | 当场完成，无在途执行 | 已提交即有结果，未提交即没有行动 |
| 出站效果 | 必须有上界与效果处理协议 | 不能以本地快照推断可以重做；随联网场景落实 |

来源的宿主装配固定提供者恢复身份、通道和物理能力；授权检查独立于这些声明。隔离执行只看到本次交付输入和私有写入范围。提供者不得让进程跨行动写入未记录的可变环境。

无效果请求可不带超时；合法的长请求无需 Kernel 统一上限。隔离执行的上界必须由宿主实际强制。timeout、停止进程和产物收齐不能依赖被执行程序自行配合。

进程内收取和重启恢复都使用接受时的提供者。改接只改变将来行动；缺少原恢复实现就停下，不静默重分派。详细接受、attempt 和终止规则在 Instance 的「执行」。

首版提供者只实现无世界效果和隔离执行；出站效果先拒绝装配，不能宣称已解决 unknown。文件、模型、其他服务分别写自己的 Port spec，不进入 Kernel 的 Port 表。

## 实现

凭据由可信宿主或提供者持有，按系统装配，本地用钥匙串或权限为 0600 的文件。凭据不进任何 Value、Journal 或执行输入。第三方服务在自己的边界负责内部状态，Kernel 记录经过通道的往来。

## 待定

- 「比相同」偏严：没有场景要求兼容，所以选严的一边。接收方自己收窄的声明过不了，如子 Agent 声明 engine 只收便宜的模型，接上的是普通的 llm；现在只能由交出的一方在自己那一侧先收窄。PauseOnly 撞上了它：熔断者自己的 reply 写的只能暂停不算，过得了，是因为登记者的 ask 在交出的一侧写了同一份。放宽到兼容是增量，要一个保守的包含判断；能放宽的先限于精确与路径前缀两种模式，因为通道强制得了；中间通配符的包含判断等价于正则语言的包含；模型名不是层级，不用前缀通配（猜）。随它定的两处记录：Correct 授予的记录不写所指 Port 的 Port spec，比相同时它等于目标那个 Required port 的 Port spec，由诞生里的 Definition 推得出；放宽之后未必相等，再作可选字段加回，是增量。到达的附带写的 spec 是所指 Port 的 Port spec，收窄过的 Correct 也写完整的那一份，链上的收窄不在记录里；接收方要知道收窄，现在只能靠自己那一节写的声明。场景：PauseOnly、角色、特许经营。
- 交出的一方写错声明时，接收方的检查过了，链上的合取却为空，错在接收方使用时以 denied 出现，要读 Journal 才追得到交出的一方。Language 的类型检查能在交出的一方提前拦下。denied 的 data 带不带违反的那一节（Port spec 的 ID 与位置），与 definition.failure 的 message、data 怎样规定一起定，也要与来路不透露中间各方一起看。没有场景。
- 联网：第一版不联网，做法在「通道」。要定的四件事。exec 怎样拿到出站的 Reference。容器里的进程能不能用模型或别的 Cognizer 的 Port，那样会绕过接在它们前面的东西，如全组预算。地址列不完的宽 Reference，如公开网络，怎样收窄：出站的白名单是一份限定，跟着持有的 Reference 走，不是一份全局名单。凭据在宿主一侧由谁持有：出站代理注入、Plugin 持有，或外部服务持有、Croon 只持有它的 Port；三者都不让凭据进数据，选哪个随提供者；正文写「凭据只在 Kernel」，Plugin 的待定写「凭据留在 Plugin 里」，要统一成一种说法。对账见 Journal 的待定「unknown 的补全」。场景：限流者、全组预算。
- 提供者环境与资源的事实怎样给检验者读取，随审计与异质检验定；每次隔离执行的输入和产物已由通用交付表达。
- 在途 Atom 的事实：交出的记录在结果回来时才写，Kernel 不记开始的时间、已收到的量，也看不见 Atom 内部的过程，如流式输出的 token、命令跑到一半的输出，那些只能由提供者给出。三处要它：时延，速度是模型服务那份 Reference 的 Competence，由 Principal 选 provider 与模型，限流与预算在 Library，Kernel 只缺数据；暂停时丢弃的生成花了钱却没有记录，Library 的预算者只看得到已记录的结果，反复暂停与解除暂停会让这部分花费看不见；流式的呈现，即边生成边看。候选：时延只要开始的时间，作为交出记录的一个字段，结果回来时一起写；丢弃的生成，接受，花费的对账交给 provider 的账单，或加一种在途的记录，暂停的 Correct 记录写明丢弃了一次在途的生成与已收到的量。在途的记录要与「还没有结果的 Atom 没有记录」一起看：它不是 Atom 的结果，重放时不参与匹配。流式要提供者在途时报出。都是增量，有速度或预算的场景出现时再加。场景：限流者、全组预算、赛马、W0 持续对话。
